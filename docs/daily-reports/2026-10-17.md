## Security and payment-safety risks

- Simulated event input is untrusted and not provider-verified; callers must not treat it as successful payment evidence.

## Concepts

- Idempotency keys protect against repeated webhook/event deliveries.
- PostgreSQL advisory transaction locks serialize work on a logical key; a unique index is the durable database invariant.
- `SIMULATED` and `NOT_APPLICABLE` prevent local test events from being confused with verified provider data.
- JSONB can normalize textual formatting, so persistence assertions should compare parsed JSON semantics.

## Later session: deterministic investigations

### Work completed

- Added `POST /api/orders/{orderId}/investigations`, which loads the order and its linked attempt/event evidence and applies deterministic rules version `1.0`.
- Retry eligibility requires every known attempt to be `PAYPAL_SANDBOX`/`FAILED` with fresh (no older than 15 minutes) verified `PAYMENT.CAPTURE.DENIED` evidence; unverified/simulated, pending, successful, unknown, missing, stale, and later event evidence blocks it.
- Provider `create_time` takes precedence; receipt time is used only if `create_time` is absent. Malformed/future timestamps are conservatively stale/unknown.
- Conflict among verified outcomes or against current order state produces `RECONCILE`; other uncertainty or a consistent success produces `WAIT`.
- Each run appends a sanitized structured evidence snapshot and an `investigation_history` row with action `CREATED` and prior decision when available. Snapshots do not contain raw payloads, provider references, or amounts. No migration or payment action was added.
- No provider/AI call is made, and no automatic charge/retry/refund behavior exists.
