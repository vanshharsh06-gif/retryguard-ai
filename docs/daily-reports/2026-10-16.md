## Database and design

- No schema changes or migrations were made.
- The service sets `CREATED`; order creation alone is not proof of a payment outcome.
- Attempt creation is metadata-only, sets status to `CREATED`, copies amount/currency from the order, and does not invoke a payment provider. Multiple rows are allowed for history.
- Duplicate detection provides a clear normal-path error, while the existing database uniqueness constraint remains necessary for concurrency safety.
- API responses use a response DTO instead of exposing the JPA entity.

## Risks and blockers

- Java 21 is needed for an unmodified project-target compile.
- A concurrent duplicate insert can race past the service pre-check and be rejected by the database constraint; that exception is not yet mapped by constraint name.
- A full HTTP-to-PostgreSQL integration test has not been performed.
- PayPal, verified webhooks, investigation, and AI behavior are not implemented by this work.

## Learning

- `BigDecimal` and `@Digits` preserve monetary precision and enforce representable scale.
- Validation belongs at the API boundary; service-level duplicate checks handle business conflict, while database constraints protect persistence invariants.
- HTTP 201 represents successful resource creation, and 409 communicates a duplicate-reference conflict.
