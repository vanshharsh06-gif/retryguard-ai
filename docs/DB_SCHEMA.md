# Database Schema Notes

The project prompt identifies these existing PostgreSQL tables: `merchant_orders`, `payment_attempts`, `payment_events`, `investigations`, and `investigation_history`. The mappings live in `src/main/java/com/retryguard_ai/entity/`.

## Merchant orders

The current `MerchantOrder` mapping specifies:

| Field | Mapping |
|---|---|
| `id` | UUID primary key, generated by JPA |
| `merchant_order_reference` | Required, unique, maximum length 100 |
| `amount` | Required decimal, precision 12, scale 2 |
| `currency` | Required three-character `CHAR` |
| `order_status` | Required string enum, maximum length 30 |
| `created_at` | Required creation timestamp, not updated |
| `updated_at` | Required update timestamp |

The persistence integration test connected to the configured PostgreSQL database, inserted an order, flushed and cleared the persistence context, then reloaded and asserted the stored fields. The test transaction rolled back, leaving no test record behind. This confirms the exercised `merchant_orders` mapping against the configured database; it is not a complete independent inventory of every live table/constraint. No migration is performed by this feature, and Hibernate schema validation remains enabled.

## Payment attempts

The current `PaymentAttempt` mapping specifies:

| Field | Mapping |
|---|---|
| `id` | UUID primary key, generated by JPA |
| `order_id` | Required many-to-one reference to `merchant_orders` |
| `provider` | Required string, maximum length 30 |
| `provider_payment_reference` | Optional string, maximum length 150 |
| `provider_capture_reference` | Optional string, maximum length 150; PayPal capture ID |
| `provider_status` | Optional string, maximum length 30; latest known raw provider status label |
| `amount` | Required decimal, precision 12, scale 2 |
| `currency` | Required three-character `CHAR` |
| `payment_status` | Required string enum, maximum length 30 |
| `failure_code` | Optional string, maximum length 100 |
| `failure_message` | Optional text |
| `created_at`, `updated_at` | Required creation/update timestamps |

The persistence integration test created and reloaded an attempt linked to its order, verified its amount, currency, provider label, and `CREATED` state, then rolled back the transaction.

The PayPal slice adds `provider_capture_reference` and `provider_status` using the additive SQL in `src/main/resources/db/migration/V2__paypal_payment_references.sql`. Earlier project notes reported V2 as unapplied. The current environment has no configured database password, so its live migration state could not be checked. Apply the SQL to the intended schema if those columns are absent before Hibernate `ddl-auto: validate` is expected to start successfully.

## Payment events

The current `PaymentEvent` mapping uses `payment_events` with a UUID key, optional attempt relationship, provider/event identifiers, event type, source/verification/processing enums, JSONB payload, received timestamp, and optional processed timestamp.

An additive partial unique index was applied to the configured local PostgreSQL database:

```sql
CREATE UNIQUE INDEX IF NOT EXISTS uq_payment_events_provider_event_id
    ON payment_events (provider, provider_event_id)
    WHERE provider_event_id IS NOT NULL;
```

Before applying it, the migration test checked that no non-null `(provider, provider_event_id)` key had duplicates. The migration is opt-in because the project does not yet have a general migration runner. The service additionally obtains a transaction-scoped PostgreSQL advisory lock per key to make duplicate handling deterministic under concurrent requests. No existing rows were changed.

Verified PayPal webhook rows reuse this key/lock. They are saved as `source_type=PROVIDER`, `verification_status=VERIFIED`, and retain the event JSON in the existing JSONB payload column. A webhook is verified before entering the transaction. Provider events with unmatched or ambiguous order/capture references remain unlinked (`payment_attempt_id=NULL`) and received; no schema change or new migration was added for webhook ingestion. JSONB may normalize the original text formatting while retaining the parsed event structure. Simulated rows remain `SIMULATED`/`NOT_APPLICABLE` and cannot change payment-attempt status through the webhook processor.

PayPal capture API responses are persisted separately as `PAYMENT.CAPTURE.RESPONSE` events with `source_type=PROVIDER` and `verification_status=NOT_APPLICABLE`. They retain the response details in JSONB, while the payment attempt stores its current capture reference/status. These response rows are visible in the existing payment timeline but are not treated as verified webhook evidence by investigations.

## Timeline data sources

No schema change was required for timeline reconstruction. The timeline reads `merchant_orders.created_at`, `payment_attempts.created_at`, and `payment_events.received_at`, along with the existing relationships and status/verification columns. Verified webhook deliveries and capture API responses are separate event rows. Payment status changes are not individually timestamped or preserved as transitions, so the timeline cannot reconstruct a complete status-change history.

## Investigation snapshots and history

Each deterministic run inserts one investigation with the versioned decision, a JSONB `evidence_snapshot`, and a JSONB `findings` array; it then inserts one `CREATED` history row with the prior decision when a previous run exists. `findings` stores typed finding DTOs with stable codes, root-cause category, severity, evidence references, non-executing operator guidance, and explicit uncertainty. The additive `V3__investigation_findings.sql` adds the JSONB column with a default empty array so existing investigation rows are preserved and remain readable.

Runs do not update or replace older snapshots or findings. Evidence snapshots and findings omit original event payloads, payment amounts, and provider payment/capture references. The `findings` field is required by Hibernate schema validation after this change. Database-backed persistence is covered by `InvestigationPersistenceIntegrationTest`, but could not run without database credentials in this environment.

Investigation reads use stable response DTOs. Order listing is bounded to the latest 50 runs and includes the order relation to avoid one query per listed result; investigation history is returned oldest first. Findings retain their actual evidence record IDs in the backend API. Gemini input includes only allowlisted finding code/category/severity/uncertainty and evidence types; it excludes evidence IDs and free-text finding/recommendation strings.

The optional Gemini explanation action reuses the existing nullable `investigations.explanation` text column. After the external call (or fallback) completes outside a transaction, a short transactional JPQL update targets only that column; decision, reason, rules version, evidence snapshot, and history are not changed. No migration is required. The update has unit/mock coverage, but a PostgreSQL-backed explanation persistence test has not been run.

## Migration sequence and current verification

The repository does not include a general migration runner or an initial create-all schema migration. Apply the additive migration files manually to the intended database after checking its actual schema: V1 (event idempotency index), V2 (PayPal reference columns), then V3 (investigation findings JSONB). V1 refuses duplicate provider event keys; do not delete or alter data to get past that check. V2 and V3 use `IF NOT EXISTS`; V3 leaves existing investigations intact and initializes their findings to `[]`.

V1 had previously been reported as applied and V2 as unapplied in project notes. The current task could not verify either state because the configured local database password was absent; the read-only `psql` schema inspection failed before connecting. V3 was not applied during this task. See the exact PowerShell migration commands in `README.md`.
